AI に「これ作って」と丸ごとお願いしたのに、出てきたものが思っていたのと少し違う。
AI と一緒に何かを作ると、一度はぶつかる場面ですよね。
でも、心配はいりません。
たいていの原因は AI の性能ではなく、<mark>作る前に「何を・どう作るか」を決めていなかったこと</mark>にあります。

それを一枚にまとめておくメモが **design.md**（デザイン・エムディー）です。

![design.md は、アイデアと実装のあいだに置く設計メモ。ずれたら design.md を直してから作り直す。](/tech/design-md.svg)

（AI に恒久的なルールを渡す [CLAUDE.md](/blog/claude-md-toha/) と混同しやすいので、違いも後で整理します。）

## design.md とは — 作る前の「設計メモ」

design.md は、何かを作りはじめる前に、<mark>「これから何を、どう作るか」を書いておく設計のメモ</mark>です。
家を建てる前の図面のようなもの、と考えてください。

CLAUDE.md が「うちではいつもこうしてね」という恒久的なルールだったのに対し、
design.md は「今回のこの機能を、こう作る」という、その場かぎりの設計図です。
作り終えて役目を果たしたら、更新するか、次の設計に置き換えていきます。

## なぜ効くのか — 方向を先に合わせる

AI は、方向がずれていても、猛スピードで突き進みます。
だから、ずれたまま作らせると、あとで大きく手戻りします。

作る前に design.md で方向を合わせておくと、この手戻りがぐっと減ります。

- 何を作るのか、ゴールがはっきりする
- 「やらないこと」も決まるので、脱線しない
- AI と人が、同じ設計図を見ながら進められる

Claude Code には、いきなり書かせず「まず計画を立てさせる」使い方（プランモード）があります。
その計画を design.md として残しておくと、次からはその図面を見ながら実装を進められます。
（→ [Claude Code の使い方](/blog/claude-code-tsukaikata/) でも「まず計画を立てさせる」コツに触れています。）

## 何を書く？ — シンプルなテンプレ

むずかしく考えなくて大丈夫です。
次のことが書いてあれば、もう十分に役に立ちます。

```md
# 作るもの
問い合わせフォームを 1 ページ追加する

## ゴール
- 名前・メール・本文を送れる
- 送信後に「ありがとうございました」を表示する

## やらないこと
- ログイン機能は今回作らない

## 画面・項目
- 入力欄：名前、メール、本文
- 送信ボタン

## 手順
1. フォームの見た目を作る
2. 送信の処理をつなぐ
3. 動作を確認する

## 注意点
- メールアドレスの形式をチェックする
```

いちばんのポイントは、<mark>「やらないこと」を書くこと</mark>です。
これがあるだけで、AI が余計な機能まで作り込むのを防げます。

## CLAUDE.md との違い

似た名前の markdown ファイルなので、役割を並べて整理しておきます。

![design.mdとCLAUDE.mdの違い。design.mdは作る前に一度書く設計メモ。CLAUDE.mdは毎回読まれる常時のルール。](/diagrams/design-vs-claudemd.svg)

| | CLAUDE.md | design.md |
| --- | --- | --- |
| 中身 | ずっと守るルール | 今回の設計図 |
| 効く範囲 | プロジェクト全体・毎回 | その機能・その作業だけ |
| 寿命 | 育て続ける | 作り終えたら役目を終える |
| たとえ | 家のルール | 一回分の間取り図 |

両方は競合しません。
<mark>CLAUDE.md で土台のルールを、design.md で今回の設計を。</mark>
役割を分けて持たせるのがコツです。

## 使うときの流れ

1. やりたいことを、ざっくり AI に相談する
2. 「まず設計だけ書いて」と頼み、design.md にまとめてもらう
3. 中身を自分の目で確認し、ずれていたら直す
4. その design.md を見せながら、実装をお願いする
5. できあがりを確認し、必要なら design.md を更新する

大事なのは、<mark>作りはじめる前に、一度立ち止まって設計をそろえること</mark>。
この一手間が、結局はいちばんの近道になります。

## 呼び名はいろいろ

「作る前に、仕様や設計を書いてから実装する」進め方は、最近 **仕様駆動開発**（Spec-Driven Development）と呼ばれ、広がっています。
requirements.md（要件）→ design.md（設計）→ tasks.md（作業）と、段階ごとにファイルを分ける流儀もあります。
また、色やフォントなど見た目のルールを機械が読める形でまとめる、Google の DESIGN.md という別物の仕様もあります。

名前や流儀はいろいろですが、芯は同じです。
<mark>いきなり作らず、設計を先に言葉にしておく。</mark>
これだけ覚えておけば十分です。

## よくある疑問

**Q. design.md と CLAUDE.md はどう違いますか？**
CLAUDE.md は毎回読まれる恒久ルール、design.md は今回の設計図（作り終えたら役目を終える）です。役割を分けて持たせます。

**Q. design.md には何を書けばいいですか？**
作るもの・ゴール・やらないこと・画面や項目・手順・注意点。とくに「やらないこと」が効きます。

**Q. 毎回 design.md を書かないとダメですか？**
いいえ。小さな作業には不要です。少し大きめの機能や、ずれが起きやすいときに、短く一枚から。

## まとめ

design.md は、AI に作らせる前に「何を・どう作るか」を書いておく設計メモです。

- 方向を先に合わせて、手戻りを減らす
- 「やらないこと」を書いて、脱線を防ぐ
- CLAUDE.md（恒久ルール）とは役割が別

いきなり「作って」とお願いする前に、まず設計を一枚。
それだけで、AI との共同作業は驚くほどスムーズになります。
次に何かを作るとき、短い design.md を書くところから試してみてください。
